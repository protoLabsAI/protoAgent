- **The A2A agent card now describes the credentials the server actually accepts (#2620).**
  A bearer-gated agent advertised `X-API-Key` as a valid alternative in
  `/.well-known/agent-card.json`, even with no API key configured anywhere. A
  standards-following A2A client is entitled to pick any advertised scheme, so one that
  chose `apiKey` got 401 from an agent that was healthy, reachable and correctly
  configured — which reads as "offline" and can block fleet onboarding and third-party
  interop. The card also presented the two schemes as OR-alternatives while the server
  checks them independently and requires **both** when both are set, so with an API key
  *and* a bearer configured neither credential alone was accepted. The card is now built
  from what the auth guard actually enforces rather than a parallel re-derivation: only
  configured schemes are advertised, both-configured is expressed as a single requirement
  naming both (an AND, which is what the middleware does), and an open agent advertises no
  credential at all instead of claiming to want one.
